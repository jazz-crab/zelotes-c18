# HID-протокол Zelotes C-18 / SOAI C18 (подмножество, используемое репозиторием)

Источник: обратная разработка `PadreAdamo/c18_reverseengineer`, живые захваты
USB и проверки на этой мыши. Здесь описано только то, что использует код.

## Устройство

- VID:PID: `12C9:2003`.
- Производитель в USB-строках: `SOAI`; продукт: `USB Gaming Mouse`.
- Композитное устройство, три HID-интерфейса:
  - `MI_00` — обычная мышь;
  - `MI_01` — system/consumer control;
  - `MI_02` — **вендорский интерфейс конфигурации**.
- Вендорский интерфейс: `usage_page = 0xFF00`, `usage = 0xFF00`,
  `bInterfaceNumber = 2`.
- Драйвер: стандартный HID Windows, Zadig/WinUSB не нужен.

## Report descriptor интерфейса 2

```
06 00 ff        Usage Page (Vendor 0xFF00)
0a 00 ff        Usage (0xFF00)
a1 01           Collection (Application)
09 20             Usage (0x20)
15 00 26 ff 00    Logical Min 0, Max 255
75 08 95 40       Report Size 8, Count 64
81 02             Input (Data, Var, Abs)      -> 64-байтовый input report
09 21             Usage (0x21)
15 00 26 ff 00
75 08 95 40
91 02             Output (Data, Var, Abs)     -> 64-байтовый output report
09 22             Usage (0x22)
15 00 26 ff 00
75 08 95 08
b1 02             Feature (Data, Var, Abs)    -> 8-байтовый feature report
c0              End Collection
```

Report ID не используется. Windows всё равно добавляет в длины по одному
байту на report ID:

| Канал | Длина данных | `HidP_GetCaps` | Что передаёт HIDAPI |
|---|---|---|---|
| feature | 8 | `FeatureReportByteLength = 9` | `00` + 8 байт |
| output | 64 | `OutputReportByteLength = 65` | `00` + 64 байта |

`00` — report ID 0; HID-класс-драйвер отбрасывает его и отправляет ровно 8 или
64 байта.

## Транзакция

Любое изменение — LED, DPI, polling, профиль — идёт по одной схеме:

```
[0x01]  begin   (фиксировано: 01 88 00 00 00 00 00 76)
[ ... ]  команда и/или 64-байтовый payload
[0x02]  commit  (02 <profile> 00 00 00 00 00 <checksum>)
```

`commit` — это не подтверждение, а настоящая команда «выбрать активный
профиль». Она же применяет изменение.

### Checksum

Для всех 8-байтовых команд:

```
checksum = 0xFF - sum(byte[0..6])
```

Сумма всех восьми байт всегда равна `0xFF`.

### 8-байтовые команды

| Opcode | Назначение | Формат |
|---|---|---|
| `0x01` | begin | `01 88 00 00 00 00 00 76` |
| `0x02` | commit / select profile | `02 <profile> 00 00 00 00 00 <cs>` |
| `0x03` | polling rate | `03 <profile> <bInterval> 00 00 00 00 <cs>` |
| `0x04` | active DPI stage | `04 <profile> <stage 1..5> 00 00 00 00 <cs>` |
| `0x0C` | prepare table write | `0C <profile> 80 00 00 00 00 <cs>` |
| `0x0D` | prepare button table write | `0D <profile> 80 00 00 00 00 <cs>` |

`bInterval` — стандартный USB-интервал в миллисекундах:

| Гц | bInterval |
|---|---|
| 1000 | `0x01` |
| 500 | `0x02` |
| 250 | `0x04` |
| 125 | `0x08` |

## LED / подсветка

64-байтовый payload отправляется на output report после `0x0C` и 64-байтового
праймера `FF FF 00 ... 00`.

Шаблон (байты 0..63):

```
0f 00 1e 0a 19 19 05 01 01 03 64 64 01 c0 f0 03
01 01 19 19 22 39 5c d0 f3 5c 73 00 22 39 5c d0
f3 5c 73 00 1f ff 00 00 00 00 31 00 00 31 00 00
31 00 00 31 00 00 31 00 00 31 00 00 31 00 00 31
```

- Блок режима — байты 4..9: `19 19 05 <mode> <speed/tier> <param>`.
- Байты 20..24 и 28..32 — пять DPI-стадий (X и Y); см. раздел DPI.
- Байты 40..63 — восемь RGB-триплетов (8 цветов).

Режимы:

| Режим | Код | speed/tier | param | Хвост |
|---|---|---|---|---|
| off | `0x00` | `0x00` | `0x00` | нули |
| static | `0x01` | 1/2/3 (high/mid/low) | `0x03` | выбранный цвет × 8 |
| breathing | `0x02` | 04/08/0C | `0x0A` | фиксированная палитра |
| neon | `0x03` | 04/08/0C | `0x00` | фиксированная палитра |
| wave | `0x04` | 03/06/09 | `0x10` | фиксированная палитра |
| flowing | `0x06` | 3C/5F/78 | `0x0A` | фиксированная палитра |

Для `static` цвет — не произвольный RGB, а бинарная маска каналов:

| Цвет | R | G | B |
|---|---|---|---|
| red | 1 | 0 | 0 |
| green | 0 | 1 | 0 |
| blue | 0 | 0 | 1 |
| yellow | 1 | 1 | 0 |
| purple | 1 | 0 | 1 |
| cyan | 0 | 1 | 1 |
| white | 1 | 1 | 1 |

Яркость задаёт «включённое» значение канала:

| Яркость | tier | on-value |
|---|---|---|
| high | `0x01` | `0x31` |
| mid | `0x02` | `0x20` |
| low | `0x03` | `0x10` |

**Выключение подсветки** — это `mode = 0x00`, `speed = 0`, `param = 0` и
нулевой хвост. Никаких отдельных команд «power off» нет.

## DPI

DPI-стадии лежат в том же 64-байтовом пакете, что и подсветка: пять байтов X
(20–24) и пять зеркальных байтов Y (28–32). Отдельной «DPI-таблицы» нет — это
тот же пакет, просто с другим набором значимых полей.

**Подтверждено на железе:** запись заводской DPI-таблицы включила подсветку в
режиме wave из её блока `19 19 05 04 06 10`. Значит, устройство применяет
весь пакет, а не только «свою» часть. Следствие: любая запись задаёт и
подсветку, и DPI; частичной записи нет. Поэтому в конфиге нет отдельных
`enabled` для подсветки и DPI.

Смещения:

| Стадия | X | Y |
|---|---|---|
| 1 | 20 | 28 |
| 2 | 21 | 29 |
| 3 | 22 | 30 |
| 4 | 23 | 31 |
| 5 | 24 | 32 |

Заводские байты — `22 39 5c d0 f3` (у профилей 1 и 2 они совпадают).
Значения `protocol.DPI_FACTORY_STAGES = (1520, 2500, 4000, 7000, 10000)`
подобраны так, чтобы кодироваться ровно в эти байты, поэтому `off` и `apply`
не меняют DPI «из коробки».

Кодирование — кусочно-линейная интерполяция по калибровочной таблице
(`protocol.DPI_CALIBRATION`, 200..10000). Активная стадия выбирается
отдельной 8-байтовой командой `0x04`.

## Кнопки

Таблица кнопок — отдельный 64-байтовый пакет. В отличие от света/DPI, он
пишется **без праймера**, но **с завершающим нулевым пакетом**:

```
begin -> 0D <profile> 80 -> 64-байтовая таблица -> 64 нулевых байта -> commit
```

Завершающий пакет обязателен. Без него прошивка остаётся в состоянии «жду
таблицу»: USB-интерфейсы и подсветка живы, но мышь перестаёт двигаться и
кликать. Это же состояние видно по `GET_REPORT` — последний opcode остаётся
`0x0D`, а `commit` игнорируется. Лечится отправкой нулевого 64-байтового
пакета (или переподключением).

Слоты (смещения 4-байтовых пар `[type LE][value LE]`):

| Слот | Смещение |
|---|---|
| 1 | 0 |
| 2 | 4 |
| 3 | 8 |
| 4 | 12 |
| 5 | 16 |
| 6 | 20 |
| 11 | 24 |
| 7 | 32 |
| 8 | 36 |
| 9 | 40 |
| 10 | 44 |

Байты 28–31 и 48–63 — фиксированный трейлер, сохраняется из заводской
таблицы. Кнопка 11 стоит между 6 и 7, а не после 10 — это особенность
раскладки вендора.

Типы действий:

| Тип | Значение | Пример действия в конфиге |
|---|---|---|
| `0x0001` | клик: `F0` left, `F1` menu, `F2` middle, `F3` back, `F4` forward | `click:middle` |
| `0x0000` | клавиша HID Keyboard/Keypad | `key:enter` |
| `mods << 8` | клавиша с модификатором: Ctrl `01`, Shift `02`, Alt `04`, Win `08` | `shortcut:ctrl+c`, `shortcut:win+shift+s` |
| `0x0003` | consumer/media: `CD` play-pause, `B7` stop, `B5` next, `B6` prev, `E2` mute, `E9`/`EA` громкость | `media:mute` |
| `0x0007` | DPI: `01` up, `02` down, `03` cycle | `dpi:cycle` |
| `0x0008` | профиль: `01` up, `02` down, `03` cycle | `profile:cycle` |

Чтения таблицы нет, поэтому каждая запись отправляет все 64 байта: конфиг
описывает нужные слоты, остальные берутся из заводской таблицы.

## Профили

- Профилей два: `1` и `2`.
- Выбираются командой `0x02`; она же коммитит изменение.
- Подсветка, DPI и кнопки привязаны к профилю. Поэтому по умолчанию конфиг
  пишет в оба профиля и оставляет активным профиль 1.
- Байты DPI-стадий у профилей совпадают (заводские `22 39 5c d0 f3`), а вот
  блок подсветки — разный: профиль 1 «из коробки» красный wave, профиль 2 —
  синий static high.

## Чтения конфигурации нет

`GET_REPORT` для 8-байтового feature-канала возвращает живой счётчик/эхо
команд (байты 3–4), а не содержимое настроек. LED, DPI, кнопки и профили —
write-only. Следствия:

- нельзя сделать backup устройства и нельзя сделать `verify`;
- «откат» — это повторная запись предыдущего конфига или заводские настройки
  через вендорскую утилиту;
- `c18 status` показывает только интерфейс, descriptor и счётчик, но не
  реальные настройки.

## Windows

- `hidapi` открывает вендорский интерфейс без замены драйвера.
- 8-байтовые команды: `hid_send_feature_report(b"\x00" + packet)`.
- 64-байтовые payload: `hid_write(b"\x00" + payload)`.
- Права администратора не нужны; вендорская утилита должна быть закрыта.
- `hid_write` возвращает 65 (длина с report ID); это нормально.

## Ограничения

- Документ описывает только LED, polling, DPI, кнопки и выбор профиля.
- Макросы и Armoury-пресеты не реализованы: там есть неподтверждённые места
  (тайминги макросов), и это не нужно для базового пресета.
- Четыре светодиода индикации DPI — аппаратные: в протоколе нет ни команды,
  ни поля, которое их выключает. Они не входят в 64-байтовый пакет.
- Поведение других прошивок не гарантируется: у мыши нет версии прошивки в
  API, поэтому перед первой записью делается только `status`/`probe`.
