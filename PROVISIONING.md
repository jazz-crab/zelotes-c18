# Регламент прошивки (Windows)

Документ описывает **как безопасно записывать конфигурацию в мышь Zelotes C-18
(SOAI C18, `12C9:2003`)** и что делать, если запись не удалась. Пока только
Windows — на ней проверяется протокол.

---

## 1. Термины

- **Прошивка (в этом репозитории)** — запись пользовательского профиля
  (подсветка, DPI, polling, активный профиль) в память мыши через HID.
  Это **не** обновление прошивки микроконтроллера и **не** перепрошивка
  загрузчика.
- **Устройство** — мышь Zelotes C-18 / SOAI C18, VID:PID `12C9:2003`,
  вендорский интерфейс `MI_02`: `usage_page 0xFF00`, `usage 0xFF00`.
- **Конфиг** — `config/default.toml`, источник истины.
- **Запись** — транзакция `begin → payload → commit`; `commit` выбирает
  активный профиль и применяет изменение.

## 2. Что делает `apply` и чего он не делает

`c18 apply --yes` пишет:

1. единый 64-байтовый пакет — подсветку (режим, цвет/яркость или эффект) и
   пять DPI-стадий;
2. активную DPI-стадию;
3. таблицу кнопок (11 слотов);
4. частоту опроса, если `polling.enabled = true`;
5. в конце — `commit` выбранного профиля.

`off --yes` пишет только пакет с LED-режимом `0x00` и DPI-байтами из конфига,
затем коммитит профиль.

Важно: у этой мыши подсветка и DPI хранятся в **одном** пакете, и устройство
применяет его целиком (проверено на железе: запись DPI-таблицы включила
подсветку из её блока). Поэтому «записать только свет» или «только DPI»
нельзя — любой write задаёт оба.

`apply` **не**:

- не обновляет прошивку MCU;
- не настраивает макросы и Armoury-пресеты;
- не управляет индикацией DPI (четыре светодиода стадий) — это аппаратная
  индикация, в протоколе для неё нет ни команды, ни поля;
- не делает backup: у устройства нет чтения конфигурации;
- не проверяет результат чтением: `verify` невозможен в принципе.

Настройки хранятся в памяти мыши: после записи вендорский софт не нужен,
переподключение и перезагрузка их не сбрасывают (пока мышь не сброшена
вендорской утилитой).

## 3. Поддерживаемая среда

| Параметр | Требование |
|---|---|
| ОС | Windows 10/11 x64 |
| Python | 3.11+ |
| Зависимости | `hidapi` (ставится из `pyproject.toml`) |
| Подключение | проводное, желательно прямой порт сзади системного блока |
| Права | обычный пользователь, администратор не нужен |
| Драйвер | стандартный HID Windows; Zadig/WinUSB **не** нужен |

Не используй RDP/USB-over-IP, виртуальные машины с пробросом USB и
некачественные хабы: запись идёт короткими HID-транзакциями, потери и
задержки там не диагностируются.

## 4. Идентификация устройства

Перед первой записью:

```powershell
py -3 -m pip install -e .
c18 status
c18 probe
```

Ожидаемо:

```
Конфиг (намерение, а не снимок устройства):
  ...
Устройство:
  SOAI USB Gaming Mouse (12C9:2003, interface 2, usage_page 0xFF00, usage 0xFF00)
  путь: \\?\HID#VID_12C9&PID_2003&MI_02...
  GET_REPORT: 00 ...
```

`probe` дополнительно печатает report descriptor. В нём должны быть:

- input report 64 байта;
- output report 64 байта;
- feature report 8 байт.

Проверить, что Windows видит мышь:

```powershell
Get-PnpDevice -PresentOnly |
  Where-Object InstanceId -like '*VID_12C9&PID_2003*' |
  Select-Object FriendlyName, Class, InstanceId
```

Должны быть HID-интерфейсы `MI_00`, `MI_01`, `MI_02`. Если `MI_02` нет —
проверь кабель, порт и что мышь не в беспроводном/спящем режиме.

## 5. Чеклист перед записью

Выполнять по порядку. Если пункт не выполняется — **не писать**.

- [ ] Мышь подключена проводом, не через hub/VM/RDP.
- [ ] Вендорская утилита SOAI/Zelotes и её фоновые процессы закрыты.
- [ ] `git status` чистый или изменения конфига осознаны.
- [ ] `c18 status` находит интерфейс `MI_02`.
- [ ] `c18 probe` показывает output 64 / feature 8 байт.
- [ ] `c18 apply` (без `--yes`) показывает правильный план.
- [ ] Питание стабильно; сон/гибернация на время записи отключены.
- [ ] Кабель не будет задет: запись идёт несколько секунд.
- [ ] Понятно, что реальное состояние подсветки можно проверить только глазами.

## 6. Почему нет backup и verify

У мыши **нет чтения конфигурации**:

- `GET_REPORT` feature-канала возвращает счётчик/эхо команд, а не настройки;
- LED, DPI, polling, профили — write-only;
- вендорская утилита тоже не даёт выгрузить сырой дамп профиля в переносимом
  виде.

Поэтому вместо backup:

1. Конфиг в git — это и есть «бэкап намерения». История `config/default.toml`
   позволяет вернуть предыдущее состояние повторным `apply`.
2. Заводские значения известны: профиль 1 — красный wave, профиль 2 — синий
   static high. Их можно вернуть вендорской утилитой.
3. Перед экспериментами сохрани текущий конфиг отдельным коммитом или файлом
   `config/local-backup.toml` (не коммить, если не хочешь).

`c18 status` — это не verify, а только проверка интерфейса и конфига.

## 7. Порядок записи

`c18 apply --yes` пишет для каждого профиля из `profile.targets`:

1. **Пакет «свет + DPI»** — `begin`, `0C <profile> 80`, праймер
   `FF FF 00...`, 64-байтовый пакет (подсветка + 5 DPI-стадий),
   `04 <profile> <stage>`, `commit`.
2. **Кнопки** — `begin`, `0D <profile> 80`, 64-байтовая таблица кнопок,
   64 нулевых байта (завершение), `commit`.
3. **Polling** — `begin`, `03 <profile> <interval>`, `commit`
   (пропускается при `polling.enabled = false`).
4. **Финальный commit** — выбранный `profile.select`.

`c18 off --yes` делает только шаг 1 с LED-режимом `0x00`.

Почему так:

- пакет (подсветка и DPI) всегда идёт после `0x0C` и 64-байтового праймера;
- между праймером, payload и commit выдерживаются паузы 20/40/50 мс;
- каждая транзакция заканчивается `commit`, иначе изменение не применится;
- `commit` — это ещё и выбор профиля, поэтому запись в два профиля меняет
  активный профиль; финальный commit возвращает выбранный.

## 8. Нормативные правила

**MUST**

1. Перед первой записью на новой машине — `c18 status` + `c18 probe`.
2. Перед каждой записью — dry-run `c18 apply` (или `c18 off`).
3. Во время записи не запускать вендорскую утилиту и не писать из двух
   процессов одновременно.
4. Не выдёргивать кабель до строки `Готово.`.
5. После записи проверить подсветку глазами (чтения состояния нет).
6. Не коммитить локальные артефакты и `config/local-backup.toml`.
7. Держать `pyproject.toml` и код в том же коммите, что и изменение конфига.

**MUST NOT**

1. Не обновлять прошивку MCU этим инструментом и не искать «reset» в CLI.
2. Не писать в устройство, если `probe` не показывает output 64 / feature 8.
3. Не запускать `apply --yes` на заблокированном/спящем компьютере.
4. Не использовать `--profile both` на мыши, где второй профиль настроен
   вручную, без понимания, что подсветка/DPI/кнопки второго профиля будут
   перезаписаны.
5. Не переносить `config/default.toml` на другую модель мыши без пересчёта
   DPI-калибровки и проверки режимов LED.

**SHOULD**

1. Для выключения подсветки использовать `c18 off --yes`: это одна запись на
   профиль, которая не трогает polling, а DPI-байты берёт из конфига.
2. Если подсветка не погасла — проверить другой профиль
   (`--profile 1` / `--profile 2`), а не менять протокол наугад.
3. Хранить в git осмысленные состояния: `off`, `static red`, эффект.
4. Не пытаться выключить индикацию DPI байтами пакета: в протоколе для неё
   нет поля, а произвольные эксперименты с нераскодированными байтами
   (`1f ff`, `64 64`) могут задеть сенсор.

## 9. Windows-специфика

- **Драйвер не нужен.** Вендорский интерфейс — обычный HID; `hidapi`
  открывает его без замены драйвера и без администратора.
- **Zadig/WinUSB не использовать.** Это сломает доступ к мыши как к HID и
  потребует переустановки драйвера.
- **Один писатель.** Закрой SOAI/Zelotes Software, AutoHotkey-скрипты,
  которые могут слать HID-отчёты, и вторые копии `c18`.
- **Report ID.** Windows требует ведущий `0x00` в буфере; код добавляет его
  сам. `hid_write` возвращает 65 — это нормально.
- **Порт.** Предпочитай порты на задней панели. Передний панельный разъём
  и дешёвый hub могут давать таймауты.
- **Сон.** Отключи сон/гибернацию на время записи; USB selective suspend не
  должен усыпить мышь между праймером и payload.
- **Кодировка.** Если в PowerShell кракозябры:
  `$env:PYTHONUTF8 = "1"` и `chcp 65001`.
- **Антивирус** обычно не мешает: запись идёт в HID, а не в файловую систему.
- **Пути.** Запускай команды из корня репозитория, иначе
  `config/default.toml` не найдётся; либо передай `--config` /
  `ZELOTES_C18_CONFIG`.

## 10. Ошибки и восстановление

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `не найден вендорский HID-интерфейс` | мышь не подключена/спит/другой порт | переподключить, другой порт, `c18 probe` |
| `не удалось открыть интерфейс` | интерфейс занят вендорской утилитой | закрыть её, переподключить мышь |
| `send_feature_report failed` | устройство отклонило 8-байтовый report | проверить `probe`, переподключить |
| `write failed` | output report не принят | проверить `probe` (output 64), другой порт |
| подсветка не погасла | записан не тот профиль | `c18 off --yes --profile 1`, затем `--profile 2` |
| подсветка стала не той | неверный режим/цвет | `c18 apply --yes` с нужным конфигом |
| DPI/ polling не изменились | запись ушла в неактивный профиль | повторить с `--profile` нужного профиля |
| мышь «зависла» | сбой USB во время записи | отключить/подключить; настройки в памяти сохранятся |
| всё сломалось после экспериментов | неверный конфиг | вернуть предыдущий `config/default.toml` из git и `apply --yes`; крайний случай — вендорская утилита / заводские настройки |

Если мышь перестала определяться совсем: отключи её, подожди 10 с, подключи в
другой порт. Профиль хранится в NVM и не должен теряться. Если устройство не
возвращается — используй вендорскую утилиту/сброс к заводским настройкам,
затем `status` и `probe`.

## 11. Откат

Три уровня, от предпочтительного:

1. **Конфиг в git.** `git checkout <commit> -- config/default.toml`, затем
   `c18 apply --yes`. Это основной способ: история конфига и есть история
   настроек.
2. **Ручной локальный конфиг.** Сохрани текущее намерение в
   `config/local-backup.toml` и при откате передай `--config`.
3. **Вендорская утилита / заводской сброс.** Крайний случай, когда нужно
   вернуть заводское состояние целиком (включая кнопки и макросы, которые
   этот репозиторий не настраивает).

## 12. Обновление прошивки мыши

Обновление MCU — отдельная операция, не в этом репозитории. У мыши нет
команды чтения версии прошивки, поэтому после обновления:

1. `c18 probe` — убедиться, что интерфейс и длины report не изменились.
2. `c18 off` (dry-run) — проверить, что план строится.
3. `c18 off --yes` — проверить на минимальной записи.
4. Если что-то не так — **не писать** дальше, пока не разобрался.

## 13. Перенос настроек на другое устройство

Этот репозиторий — про Zelotes C-18 / SOAI C18. При смене мыши:

1. Скопируй `config/default.toml` как черновик намерения.
2. Пересчитай DPI-калибровку под новую модель (она не универсальна).
3. Проверь режимы LED и формат payload: у другой мыши он почти наверняка
   другой.
4. Сделай отдельный репозиторий/конфиг под новое устройство, а этот не ломай.

## 14. Что коммитить

Коммитить:

- `config/default.toml`;
- `src/`, `tools/`, `docs/`, `README.md`, `PROVISIONING.md`,
  `pyproject.toml`.

Не коммитить:

- `__pycache__/`, `.venv/`, `*.egg-info/`;
- `config/local-backup.toml` (личный снимок намерения).

## 15. Финальный чеклист

```powershell
c18 status
c18 probe
c18 apply              # dry-run: свет, DPI и кнопки
c18 apply --yes
```

Ручная проверка после записи:

- [ ] подсветка погасла (или включилась та, что в конфиге);
- [ ] мышь двигается и кликает как обычно;
- [ ] кнопки 4–11 делают то, что в `[buttons]` (copy/paste, скриншоты и т.д.);
- [ ] DPI соответствует конфигу;
- [ ] если подсветка не погасла — проверен второй профиль.

## 16. Проверенный сценарий

На реальной мыши (Windows 11, `12C9:2003`, профили 1 и 2) выполнено:

```powershell
c18 status      # интерфейс MI_02 найден, descriptor 48 байт
c18 probe       # input 65 / output 65 / feature 9 (включая report ID)
c18 apply       # dry-run: свет + DPI + кнопки
c18 apply --yes
```

Пресет: подсветка `off`, DPI 2500 на всех пяти стадиях, кнопки 4=Paste,
5=Copy, 6=Play/Pause, 7=Alt+Tab, 8=Enter, 9=Ctrl+Z, 10=Win+Shift+S,
11=PrintScreen. Polling не трогали (`polling.enabled = false`).

Результат: декоративная подсветка погасла полностью, мышь продолжила
работать штатно, кнопки и DPI применились в обоих профилях.
`GET_REPORT` после записи сменился с `00 00 00 00 00 00 00 00 00` на
`00 02 02 00 c0 20 00 00 00` — это счётчик команд, а не подтверждение
настроек.

Отдельно проверено, что пакет общий: запись заводской DPI-таблицы в профиль 1
включила подсветку в режиме wave из её блока `19 19 05 04 06 10`. После этого
код переделан так, чтобы каждая запись строила единый пакет «свет + DPI».

Вывод: для полного пресета достаточно `c18 apply --yes`; писать в один
профиль не нужно, оба профиля принимают настройки.

Индикация DPI при этом остаётся: это четыре отдельных светодиода стадий,
которые прошивка включает сама. В вендорской утилите и в протоколе нет
настройки, которая их выключает.

Win+Scroll → громкость прошивкой не делается (колесо — HID-ось, а состояние
Win на клавиатуре мыши недоступно). Это только хост-хук:
`tools/win-scroll-volume.ahk` для AutoHotkey v2.

Отдельный случай: первая версия записи таблицы кнопок не отправляла
завершающий нулевой пакет, и мышь зависла — USB и подсветка живы, но ввод
не идёт, а `GET_REPORT` показывает последний opcode `0x0D`. Нулевой пакет
разбудил устройство без переподключения. Теперь он отправляется всегда
(`transaction_buttons`), и зависание не повторяется.
